Database Seeding Concepts

Foundational Overview

What is Database Seeding?

Database seeding populates your database with essential initial data, making the application functional after schema creation.

Schema vs. Seeding

  • ›Alembic ensures database "shape" (tables, columns).
  • ›Seeding populates initial required data.
  • ›Empty schemas lack immediate functionality.

Key Purposes

  • ›Provides static reference data for logic.
  • ›Bootstraps sample data for dev environments.

Data Categories

Seed Data Categories

Differentiating between reference data and mock data ensures the right information populates your database for its intended purpose.

Reference Data (Foundational)

  • ›Lookup data required for application runtime.
  • ›Roles, membership types, subscription plans.

Development/Mock Data

  • ›Simulates production environments for testing.
  • ›Dummy users, schedules, locations.

Reference Data

Primary Goal: Reliability

Essential for schema constraints. Without this, your application crashes when trying to assign a 'User' to a 'Role' that doesn't exist.

Development Data

Primary Goal: Velocity

Used to populate charts, lists, and profiles so developers don't have to manually create 100 users to test pagination.

Seeding Mechanism

The init.sql Seeding Mechanism

Foundational seed data is managed in init.sql, acting as the authoritative source that must remain synchronized with application Enums.

init.sql Role

  • ›Defines "Day 0" foundational state.
  • ›Located in gms_be/gmsshared/db/init.sql.

Data in init.sql must align perfectly with Python Enums; otherwise, serialization fails.

INSERT INTO roles (id, name, description) VALUES 
(1, 'super_admin', 'Full system access'),
(2, 'gym_owner', 'Access to specific gym locations'),
(3, 'staff', 'Daily operations access'),
(4, 'member', 'Standard member access')
ON CONFLICT (id) DO NOTHING;
Migrations vs Seeding

Seeding vs. Schema Migrations

Use Alembic migrations for data tied to schema changes, and init.sql for core system parameters and initial setup.

Alembic Migrations

Best for data transformations, column renames, and structural evolutions over time.

init.sql Seeding

Best for static reference tables and environment bootstrapping from scratch.

Keeping init.sql separate streamlines environment setup for new developers.

Alembic Focus

Typical Usage

Modifying table structure and migrating existing data to the new shape.

Frequency

Run incrementally every time the codebase changes.

Operational Lifecycle

Operational Lifecycle & Idempotency

Seeding scripts must be idempotent, running safely multiple times, and are applied after schema migration during container startup.

Container Initialization Sequence

  • 1DB Engine Starts
  • 2Alembic Upgrade Head
  • 3init.sql Execution

Idempotency Requirement

  • ›Must run multiple times without duplication.
  • ›Achieved via ON CONFLICT logic.

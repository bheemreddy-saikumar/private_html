Understanding Migration Scripts

Mastering the structure of `.sql` files for reliable database schema evolution.

Migration Basics

Foundations of SQL Migrations

SQL migration files are structured with up and down sections to manage database schema evolution systematically.

Purpose of Migration Scripts

  • ›Version control system for database schema.
  • ›Handle orchestration and versioning logic.
  • ›Represent discrete, immutable steps in evolution.

Standard Structure

  • ›Bifurcated into migrate:up and migrate:down blocks.
  • ›Markers indicate application or reversion commands.

Version Control Logic

Treats DB changes like Git commits: each file is a unique, trackable point in time.

The Bifurcation Rule

Every forward change (up) requires an explicit reverse instruction (down) for recovery.
Up Block

Advancing the Schema

The migrate:up section defines the DDL and DML needed to advance the database schema to version n+1.

Function of `migrate:up`

  • ›Transforms the database from version n to n+1.
  • ›Used for creating tables and establishing indexes.

Key Responsibilities

  • ›Schema alterations: Adding columns, managing constraints.
  • ›Data migrations: Transforming data for new structures.
-- migrate:up
CREATE TABLE gym_locations (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    gym_id UUID NOT NULL REFERENCES gyms(id) ON DELETE CASCADE,
    name VARCHAR(255) NOT NULL,
    address TEXT,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX idx_gym_locations_gym_id ON gym_locations(gym_id);
Down Block

Reverting Changes Safely

The migrate:down section contains the inverse operations of migrate:up, enabling the database to return to its previous state.

Purpose of `migrate:down`

  • ›Returns the database to its exact prior state.
  • ›Critical for local branch switching and recovery.

Practical Constraints

  • ›Destructive risk: Potential data loss on item drops.
  • ›Order of operations: Must reverse the "up" sequence.
-- migrate:down
DROP TABLE IF EXISTS gym_locations;
Best Practices

Reliability & Best Practices

Migrations must adhere to idempotency and immutability to ensure reliable CI/CD pipelines across all environments.

Data Manipulation (DML)

  • ›Used for one-time "backfilling" of required data.
  • ›Wrap in transactions for atomic safety.

Structural Hygiene

  • ›Idempotency: Use `IF NOT EXISTS` clauses.
  • ›Immutability: Never edit a deployed file.

Trade-offs

Speed vs. Integrity

Balancing deployment speed with data integrity often requires 'online DDL' techniques to minimize production downtime.

Online DDL Patterns

  • ›Add nullable columns first.
  • ›Backfill in small batches to avoid locks.
  • ›Apply constraints only after population.
